`viga/websocket` adiciona comunicação em tempo real à sua aplicação: o servidor e o navegador mantêm uma conexão aberta e trocam mensagens nos dois sentidos. Serve para chats, notificações, painéis que se atualizam sozinhos ou jogos.

Funciona na mesma porta da sua API HTTP e com as mesmas peças: os gateways são providers com `inject()`, as mensagens são validadas com schemas e os erros usam os mesmos códigos que no HTTP.

## Seu primeiro gateway

Um gateway está para o WebSocket como um controller está para o HTTP: recebe as mensagens de um caminho e responde. Cada método atende um evento:

```ts title="src/chat/chat.gateway.ts"
import { inject } from 'viga';
import { Gateway, OnMessage, WsServer, type WsContext } from 'viga/websocket';
import { z } from 'zod';

const Join = z.object({ room: z.string().min(1) });
const Say = z.object({ room: z.string(), text: z.string().max(500) });

@Gateway('/chat')
export class ChatGateway {
  private readonly server = inject(WsServer);

  @OnMessage('join', Join)
  join({ client, data }: WsContext<typeof Join>) {
    client.join(data.room);
    return { joined: data.room };
  }

  @OnMessage('say', Say)
  say({ client, data }: WsContext<typeof Say>) {
    this.server.to(data.room).send('said', { from: client.state.userId, text: data.text }, { except: client });
  }
}
```

- `@Gateway('/chat')` define o caminho: os clientes se conectam a `wss://seu-dominio/chat`.
- `@OnMessage('join', Join)` atende o evento `join` e valida seus dados com o schema `Join`.
- `WsContext<typeof Join>` tipa `data` com a forma do schema, igual a [`HttpContext`](../validation/#valide-uma-rota) no HTTP.

Os gateways são providers: são declarados em `providers` de um módulo, não em `controllers`:

```ts title="src/chat/chat.module.ts"
import { Module } from 'viga';
import { ChatGateway } from './chat.gateway.ts';

@Module({ providers: [ChatGateway] })
export class ChatModule {}
```

E `WebSocketModule.forRoot` vai no módulo raiz, com a autenticação e as origens permitidas:

```ts title="src/app.module.ts"
import { Module } from 'viga';
import { WebSocketModule } from 'viga/websocket';
import { ChatModule } from './chat/chat.module.ts';

@Module({
  imports: [
    WebSocketModule.forRoot({
      authenticate: (req) => verifySession(req.headers.cookie),
      allowedOrigins: ['https://meu-frontend.com'],
    }),
    ChatModule,
  ],
})
export class AppModule {}
```

## A partir do navegador

O navegador usa o `WebSocket` que já vem com ele. As mensagens são JSON com um `event`, os `data` e, se você quiser resposta, um `id`:

```ts title="chat.js"
const socket = new WebSocket('wss://api.meu-dominio.com/chat');

socket.addEventListener('open', () => {
  socket.send(JSON.stringify({ event: 'join', data: { room: 'general' }, id: 1 }));
});

socket.addEventListener('message', (event) => {
  const message = JSON.parse(event.data);
  console.log(message.event, message.data);
});
```

Se a aplicação tiver `globalPrefix`, ele não se aplica aos gateways: o caminho é o de `@Gateway`.

## As mensagens

### Respostas

O que o método devolve é enviado de volta ao cliente com o mesmo evento e o mesmo `id`, para que ele saiba a qual mensagem corresponde:

```json
{ "event": "join", "data": { "joined": "general" }, "id": 1 }
```

Se o método não devolver nada, como `say`, nenhuma resposta é enviada.

Um método `async function*` envia uma mensagem por cada valor que produz, útil para resultados que chegam aos poucos:

```ts
@OnMessage('progress')
async *progress() {
  yield { step: 1 };
  yield { step: 2 };
}
```

### Erros

Os erros chegam como uma mensagem com o evento `error`, com os mesmos códigos e o mesmo formato das [exceções](../../core/exceptions/):

```json
{
  "event": "error",
  "data": {
    "statusCode": 400,
    "code": "errors.validation",
    "message": "Invalid input data",
    "details": { "data": [{ "path": "room", "code": "too_small", "message": "Too small: expected string to have >=1 characters" }] }
  },
  "id": 2
}
```

Um evento que não existe responde `errors.notFound`. Como no HTTP, os erros inesperados nunca enviam sua mensagem interna ao cliente.

### Um evento sem schema não aceita dados

Um evento que não recebe dados, como `progress`, não precisa de schema. Se um cliente lhe enviar uma mensagem com `data`, o viga responde com um erro 400 de código `errors.unexpectedData`, sem chamar o método:

```json
{ "event": "error", "data": { "statusCode": 400, "code": "errors.unexpectedData", "message": "This event does not accept data" }, "id": 3 }
```

Assim nenhum dado sem validar chega aos seus métodos: um evento que recebe dados precisa declarar seu schema em `@OnMessage`. É a mesma regra de `errors.unexpectedBody` nas [rotas HTTP](../validation/#toda-rota-com-corpo-precisa-de-validate).

Esse comportamento se chama `requireValidation` e está ativado por padrão. Com `WebSocketModule.forRoot({ requireValidation: false })`, os eventos sem schema recebem `data` como chega.

## Salas

Uma sala agrupa conexões para enviar mensagens a todas de uma vez:

- `client.join(room)` e `client.leave(room)` adicionam ou removem o cliente de uma sala, e `client.rooms` diz em quais ele está. Um cliente pode estar em várias, e sai de todas ao se desconectar.
- `inject(WsServer).to(room).send(event, data)` envia para todos os clientes de uma sala. Com `{ except: client }`, para todos menos esse.
- `inject(WsServer).broadcast(event, data)` envia para todos os clientes conectados.

`WsServer` pode ser pedido a partir de qualquer provider, não só dos gateways. Assim um serviço pode avisar os clientes quando algo muda, por exemplo ao criar um pedido a partir de uma rota HTTP.

:::caution
As salas vivem na memória do processo. Se a sua aplicação roda em várias instâncias, uma mensagem enviada a uma sala só chega aos clientes conectados a essa mesma instância.
:::

## Autenticação

Um WebSocket é autenticado uma única vez, ao se conectar, no handshake. `authenticate` recebe essa requisição e devolve os dados da sessão, ou `false` para rejeitá-la com 401:

```ts
WebSocketModule.forRoot({
  authenticate: async (req) => {
    const session = await sessions.find(req.headers.cookie);
    return session ? { userId: session.userId } : false;
  },
}),
```

O que ela devolve fica em `client.state`, disponível em todas as mensagens dessa conexão: `client.state.userId`.

Assim como as rotas HTTP, os gateways são privados por padrão: sem `authenticate`, só aceitam conexões os que têm [`@Public()`](../../core/guards/). Ao iniciar, o viga avisa sobre os gateways privados sem autenticação e lista os públicos com nível `debug`.

:::note
O `WebSocket` do navegador não pode enviar cabeçalhos próprios, então `Authorization` não serve. O handshake só leva a URL, os cookies, `Origin` e `Accept-Language`. Autentique com o cookie de sessão ou, se não puder, com um token de vida curta na URL, sabendo que as URLs costumam ficar nos logs.
:::

### Sessões que expiram

Como a autenticação só acontece ao se conectar, uma conexão aberta continuaria funcionando mesmo depois de a sessão expirar. Para evitar isso, devolva `expiresAt` em `authenticate`, como uma data ou em milissegundos:

```ts
authenticate: async (req) => {
  const payload = await verifyToken(tokenFrom(req));
  return payload ? { userId: payload.sub, expiresAt: payload.exp * 1000 } : false;
},
```

Nesse horário, o viga fecha a conexão com o código 1008 `Session expired`. Se o cliente renovar o token pelo próprio socket, atualize a expiração com `client.expireAt(novaData)`.

Para encerrar uma sessão imediatamente, por exemplo ao mudar a senha, percorra `inject(WsServer).clients` e feche os desse usuário com `client.close()`.

### Origens permitidas

`allowedOrigins` lista os sites a partir dos quais um navegador pode se conectar. Uma conexão com outro `Origin` é rejeitada com 403. Isso evita que uma página maliciosa abra um WebSocket com os cookies do seu usuário, um ataque chamado *cross-site WebSocket hijacking*.

As conexões sem `Origin`, que vêm de clientes que não são navegadores, como um servidor ou um app móvel, são aceitas.

## Guards, interceptores e limites por evento

As mesmas ferramentas do HTTP funcionam em cada mensagem:

- [`@UseGuards()`](../../core/guards/#guards-por-rota) e [`@UseInterceptors()`](../../core/interceptors/) vão em um método ou no gateway inteiro.
- `RateLimit`, importado de `viga/websocket`, limita um evento ou todos os de um gateway. Por padrão conta por conexão; com `key: ({ client }) => String(client.state.userId)` conta por usuário, somando todas as suas abas. Acima do limite responde `errors.tooManyRequests` com `details.retryAfter` em segundos.

O `@RateLimit` importado de `viga` é só para rotas HTTP.

### Conexões e desconexões

Um gateway pode executar código quando um cliente se conecta ou se desconecta, implementando `OnWsConnection` e `OnWsDisconnect`:

```ts
import { Gateway, type OnWsConnection, type OnWsDisconnect, type WsClient } from 'viga/websocket';

@Gateway('/chat')
export class ChatGateway implements OnWsConnection, OnWsDisconnect {
  onConnection(client: WsClient) {
    client.join(`user:${client.state.userId}`);
  }

  onDisconnect(client: WsClient, code: number, reason: string) {
    this.presence.markOffline(client.state.userId);
  }
}
```

## Idioma

Se você passar uma instância de [`viga/i18n`](../i18n/) na opção `i18n`, o idioma é escolhido uma vez, ao se conectar, e usado em todas as mensagens dessa conexão: `i18n.t()` funciona dentro dos gateways, os erros saem traduzidos e `client.locale` contém o idioma.

O navegador não permite enviar cabeçalhos próprios, então para que o usuário escolha o idioma, leia-o da URL com `resolveLocale`:

```ts
WebSocketModule.forRoot({
  i18n,
  resolveLocale: (req) => new URL(req.url ?? '/', 'http://localhost').searchParams.get('lang'),
}),
```

## Limites por padrão

`viga/websocket` traz limites para que um cliente não consiga esgotar a memória nem as conexões do servidor. Todos são alterados em `WebSocketModule.forRoot`:

| Opção | Padrão | O que limita |
| --- | --- | --- |
| `maxConnections` | `10_000` | Conexões simultâneas no total. Acima disso, o handshake responde 503. |
| `connectionsPerKey` | `{ max: 50 }` | Conexões simultâneas por cliente, por IP por padrão. Acima disso, responde 429. `key` permite contar por outra coisa, e `false` o desativa. |
| `maxPendingHandshakes` | `100` | Handshakes em andamento ao mesmo tempo. Evita que uma avalanche de conexões dispare milhares de autenticações em paralelo. |
| `handshakeTimeoutMs` | `10_000` | Quanto `authenticate` pode demorar. Se demorar mais, responde 503. |
| `maxPayload` | 100 KiB | O tamanho de uma mensagem. Uma maior fecha a conexão. |
| `messageRateLimit` | `{ max: 100, windowMs: 10_000 }` | Mensagens por conexão. Acima disso responde `errors.tooManyRequests`, e ao dobro desconecta o cliente. |
| `maxRoomsPerClient` | `100` | Salas em que uma conexão pode estar. |
| `maxBufferedBytes` | 1 MiB | Mensagens pendentes de um cliente que não as lê. Acima disso, ele é desconectado. |
| `heartbeatMs` | `30_000` | A cada quanto tempo se verifica que o cliente continua vivo. Um que não responde é desconectado. |

`connectionsPerKey` usa o IP do cliente conforme a opção `trustProxy` da aplicação. Atrás de um proxy, configure-a corretamente: senão, todos os clientes compartilhariam o IP do proxy e o mesmo contador.

## Outros adaptadores

Por padrão, `viga/websocket` usa `ws`, e o navegador se conecta com seu `WebSocket` normal. A opção `adapter` aceita qualquer implementação da interface `WsAdapter`, que é pública, para usar outra biblioteca sem mudar seus gateways. Mudar de adaptador muda o cliente: com socket.io, por exemplo, o navegador precisa de `socket.io-client`.
